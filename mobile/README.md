# Tap In phone app

A thin native shell (Capacitor 8) around the Tap In web app. The shell opens `https://www.tap-in.world/app/` inside a
full-screen web view, so the app is always the same code as the website and updates the moment the Worker is deployed.
What the shell adds is what a web page cannot do on its own: the store listing, the status bar and splash, light
haptics, links to tap-in.world opening in the app, and (next) the native features listed under "Next".

```
mobile/
  capacitor.config.json   app id world.tapin.app, the live URL it loads, allowed hosts
  www/index.html          fallback page (Capacitor needs a webDir; the live site is what people see)
  android/  ios/          the two native projects (generated by Capacitor, then edited: see below)
  assets/                 source icon and splash images; `npm run assets` makes every size
  deeplinks/              templates for the two files that let links open the app (see "Links open the app")
../worker/public/js/native.js   runs inside the app only; does nothing in a browser
../worker/public/app/manifest.webmanifest   makes /app/ installable from a browser too
```

## What is already done
- `/app/` is an installable web app: standalone, its own icons, an "Install" card on the Me tab (Android) and the
  "Share, then Add to Home Screen" steps on iPhone. It is hidden once installed.
- Both native projects exist with icons and splash screens made from the logo.
- Android: camera permission (gate scanning and the guest photo), `allowBackup` off, and App Links for
  `www.tap-in.world` and `tap-in.world` on `/app/`, `/signin/` and `/i/`.
- iPhone: the camera usage text is in `Info.plist`.
- `.github/workflows/mobile.yml` builds a debug APK on every change under `mobile/` (download it from the run's
  Artifacts). The iPhone build runs only when started by hand.

## Build it
You need Node 22. For Android: JDK 21 and the Android SDK (or Android Studio). For iPhone: a Mac with Xcode.

```bash
cd mobile
npm ci
npm run assets          # only after changing assets/
npx cap sync            # copies config and plugins into both projects
npm run android:build   # debug APK in android/app/build/outputs/apk/debug/
npm run ios:open        # opens Xcode (Mac only)
```

## Before the first store release
1. **App id.** `world.tapin.app` is in `capacitor.config.json`, `android/app/build.gradle` and the Xcode project. Change it
   now if you want a different one: it cannot change after publishing.
2. **Accounts.** Apple Developer Program (US$99 a year) and Google Play Console (US$25, once).
3. **Signing.** Android: create an upload key and turn on Play App Signing. iPhone: choose the team in Xcode.
4. **Links open the app.** Fill in the two files in `deeplinks/` and serve them from the website:
   - Android: `/.well-known/assetlinks.json` with the SHA-256 of the Play app signing key.
   - iPhone: `/.well-known/apple-app-site-association` (no extension, `application/json`) with your Apple Team ID, and add
     the **Associated Domains** capability in Xcode with `applinks:www.tap-in.world` and `applinks:tap-in.world`.
   Until then the app still works; links just open in the browser.
5. **Store listing.** Privacy policy URL (`/privacy/`), screenshots, age rating, data-safety / privacy labels.

## How sign-in works in the app
The emailed sign-in link opens in the browser, and a browser cannot hand its session to an app. So the app and the
browser meet through a one-time note (`app_logins`, migration `0012`):

1. The app makes a random secret, keeps it on the device, and sends only its SHA-256 (the *challenge*) when it asks for the link. The
   challenge rides in the emailed link as `?ac=`.
2. The person opens the link. The browser signs in as usual, then leaves a note keyed to the challenge and says "go back to the app".
3. The app, still waiting on its "Check your email" screen, shows the secret to `POST /api/auth/app/redeem`. If the note is there
   it gets its own session; otherwise it is told "not yet" and asks again. The note works once and lasts 10 minutes.

Why this is safe: the challenge is in the email, but only the app holds the secret behind it, so seeing the link is not enough to
collect the sign-in. The first note for a challenge wins while it is valid, so another account cannot replace it. The wait
survives the app being closed (the secret is kept in storage for about an hour, the life of the emailed link). The same flow
serves an installed web app. Code: `worker/src/routes/auth.js` (`appRedeem`), `worker/public/js/applogin.js`,
`worker/public/js/auth-ui.js`, `worker/public/signin/signin.js`; tests in `worker/test/applogin.mjs`.

Deploying this needs the migration first: `npm run db:migrate:remote` in `worker/`, then `npx wrangler deploy`. The daily clean-up
reads the new table, so the code must not go out before it exists.

## Known problems to decide before release
- **Apple review.** A shell that only shows a website can be rejected (guideline 4.2). The native features under "Next"
  are what make it pass. Apple also requires an in-app "Delete my account" if people can create accounts here.
- **Wallet passes cannot show Live QR** (the code changes every 30 seconds). The app can, and does, make its own code on the
  phone.
- **Payments** are off (`PAYMENTS_MODE`). If top-ups or tickets for digital goods return, check each store's
  in-app purchase rules. Tickets for real-world events are normally exempt.
